# Headless S3 workspaces

This fork of OpenCode v2.2.1 can serve one S3 bucket/prefix as its workspace.
It uses `s3mini@1.0.3`; it is not an official OpenCode storage integration.

## Start

Set the server environment, supplying credentials through your secret manager:

```sh
export OPENCODE_S3_ENDPOINT=https://s3.example.com/my-bucket
export OPENCODE_S3_BUCKET=my-bucket
export OPENCODE_S3_PREFIX=workspaces/example
export OPENCODE_S3_ACCESS_KEY_ID=...
export OPENCODE_S3_SECRET_ACCESS_KEY=...
export OPENCODE_S3_REGION=us-east-1
bun run dev serve --hostname 127.0.0.1 --port 4096
```

The endpoint includes the bucket, using either path-style or virtual-hosted
addressing. The prefix and region are optional. Partial S3 configuration fails
startup rather than starting a local-filesystem server. Do not expose the API
without the usual OpenCode authentication and network controls.

The virtual root is `/workspace`. For example, `/workspace/documents/report.pdf`
maps to `s3://my-bucket/workspaces/example/documents/report.pdf`. Upload objects
to that prefix before referring to them. The server does not create buckets.

## HTTP inputs

Use the existing session and filesystem APIs. Omit the session location to use
the virtual root, or specify a directory beneath `/workspace`.

```json
{
  "text": "Review this uploaded report",
  "files": [
    {
      "uri": "s3://my-bucket/workspaces/example/documents/report.pdf"
    }
  ]
}
```

Submit that body to `POST /api/session/<session-id>/prompt`. Add `"resume": false`
to admit the input without starting model execution. Virtual `file:///workspace/…`
attachments also read S3, never the server host. Other buckets/prefixes and
missing objects are rejected. Existing attachment MIME processing and the
20 MiB attachment limit remain in effect.

## Behavior and limits

- Read, write, edit, patch, listing, glob, find and grep use workspace objects.
- Grep feeds object bytes into the server's `rg` executable without downloading
  a local workspace. The executable remains host infrastructure.
- Directories are implicit prefixes or zero-byte objects ending in `/`.
- Moves are copy/delete operations, not atomic renames. Multi-file patches can
  partially apply, as with the existing file tools.
- Writes overwrite existing objects. Run only one writer per prefix; there is
  no distributed lock or optimistic-concurrency guarantee.
- Workspace instructions and retained tool output use S3. Application state,
  authentication, executable caches and the session database remain host-local.
- Backend-specific database identity isolates this profile from local sessions.
- Shell/build execution, PTY, Git/worktrees, external formatters and Git-backed
  snapshots are unavailable for S3 workspaces.
- No TUI or desktop integration is added.

## Verification

Install a MinIO test binary separately and put it on `PATH`, or set
`OPENCODE_TEST_MINIO_BINARY` to its executable path. The integration tests start
their own loopback-only MinIO process on an ephemeral port, create a private
bucket with random credentials, and remove the process and data afterward.
They do not download binaries or require any cloud credentials during tests.
An explicitly configured invalid binary fails setup rather than skipping.

Set `OPENCODE_TEST_REQUIRE_S3=1` to require this coverage. In that mode a missing
MinIO dependency fails immediately, and external S3 endpoint configuration is
rejected. The dedicated `check-hermetic` CI workflow provisions pinned tools
first, then runs the tests with loopback networking only on a standard
GitHub-hosted runner; Blacksmith is not required.

For optional interoperability checks against a separately managed disposable
endpoint, the tests also accept the following variables.

The real-endpoint tests accept `OPENCODE_TEST_S3_ENDPOINT`,
`OPENCODE_TEST_S3_BUCKET`, `OPENCODE_TEST_S3_ACCESS_KEY_ID`,
`OPENCODE_TEST_S3_SECRET_ACCESS_KEY` and optional `OPENCODE_TEST_S3_REGION`.
Use a disposable bucket; tests create isolated prefixes and clean their own
objects. Run tests from the owning package, not the repository root.

```sh
# From packages/core:
OPENCODE_TEST_REQUIRE_S3=1 bun run test test/environment-s3.test.ts test/tool-s3.test.ts
# From packages/server:
OPENCODE_TEST_REQUIRE_S3=1 bun run test test/s3-integration.test.ts
```

Use the package test scripts rather than invoking `bun test` directly: the
scripts isolate HOME, XDG directories, configuration and credentials. OAuth
callback policy tests use injected listener behavior and a controlled clock;
socket integration tests use private ephemeral ports, never the developer's
live callback listeners on ports 1455/1457.
